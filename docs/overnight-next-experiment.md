## Assessment

The first training batch provides real RL signal, but it does not diagnose a model-size bottleneck. Its 24 episodes supplied 346 sampled actions with positive and negative advantages in every environment. All eight maze episodes ended at the distance cutoff; seven chess episodes ended at material adjudication and one at insufficient material. The policy chooses a single action label with thinking disabled. Paying for a larger model before checking that interface would confound capacity with reasoning time and available computation.

Recommended priority: **complete the two-cycle audit; screen thinking and executable policies with the existing 8B model; then decide whether a larger learner is justified.** Qwen3-8B supports both thinking and non-thinking modes, so this comparison does not require new model weights. [Qwen3-8B model card](https://huggingface.co/Qwen/Qwen3-8B)

Game self-play can transfer to broader capabilities, but that remains an empirical question. SPIRAL uses generated reasoning and multi-turn RL; our direct-action setup differs. It also reports substantial compute and eventual plateaus. [SPIRAL](https://arxiv.org/abs/2506.24119)

## Decision gates

1. **Integrity gate:** finish both active cycles, replay every episode, verify private-observation boundaries and checkpoint hashes, and check finite optimizer metrics. Preserve the run even if it is negative. If any correctness check fails, fix the next version and rerun a smoke test; do not scale the faulty result.
2. **Learning gate:** compare all checkpoints against the same frozen opponents, with paired scenario differences, absolute P&L, actual goals/checkmates, and cutoff rates. Self-play's mean reward is zero by construction. A larger adapter delta or higher league rank alone is not improvement. The three-seed pilot is too small to promote a scientific claim.
3. **Interface gate:** use fresh development seeds to compare the same base 8B model in direct-action, thinking-enabled action, and generated-code modes. Start with one scenario and both seats per game per mode (six games per mode). If valid and fast enough, extend to four paired development scenarios per game. Stop screening at a declared two-hour wall-clock cap; an unfinished arm is inconclusive. Record actual tokens, latency, and CPU execution cost rather than calling unlike compute budgets equal.
4. **Capacity gate:** test a larger model only if a well-specified interface still performs poorly, or if a strong API opponent/teacher succeeds in exactly the same environment and observation interface. The latter diagnoses potential headroom, not proof that model size alone explains the gap. A same-family Qwen3-14B QLoRA run is a clean capacity comparison; it is not a claim to use the newest or strongest available open model. [Qwen3-14B model card](https://huggingface.co/Qwen/Qwen3-14B)
5. **Continuation gate:** authorize at most three additional training cycles in a new run manifest. Use a development promotion criterion fixed before sampling: finite updates, reproducible outputs, and improvement on at least two games without a material regression on the third. Specify a numerical tolerance in the new manifest; this is an operational gate, not statistical proof. Stop on two successive development regressions, nonfinite updates, corrupted replay, exhausted runtime, or the spending boundary. Do not keep searching configurations against the final test set.

For new reasoning runs, record every sampled reasoning/action token and its behavior log-probability. If only the final label is optimized while reasoning is generated by the changing policy, the trainer must account for that mismatch; the existing one-token trainer cannot simply be reused unchanged. Truncations and formatting errors remain separate from strategic losses.

The current short-horizon objectives may remain useful as diagnostic games. Test longer maze/chess horizons in a separately named environment version when genuine finishing behavior is the objective. Re-evaluate baseline checkpoints under that version; do not combine its ratings with the old capped-game ratings.

## Executable strategies

Have a model generate an algorithm implementing a narrow interface such as `act(observation, legal_actions, memory) -> (action, memory)`. The executable receives only the same visible observation that a direct-action model receives. It can plan, maintain state, search a public chess position, or calculate trading decisions, but cannot inspect simulator private state, future randomness, opponent memory, or evaluation seeds.

Use a real isolated process/container with no credentials or network, a read-only runtime, a bounded writable scratch directory, bounded CPU time and memory, and validated JSON inputs/outputs. A Python AST allowlist alone is not an isolation boundary. Invalid code, illegal actions, timeouts, and strategic losses must be reported separately. All policy variants receive declared computation budgets.

Start with at most four independently sampled programs per game, each evaluated on the same development scenarios. Keep every sample and score; do not report only the best program as typical model performance. A corrected or selected program is a new policy version with a new hash and rating. The initial test answers whether programming exposes capabilities hidden by single-token decisions.

**Generating and revising programs with an API is not model-weight RL.** For actual RL of the code-generating model, treat a sampled program as a temporally extended action: save its token probabilities, evaluate it over several training scenarios, compute return/advantage across programs, and update the open-weight generator. Programs from DeepSeek or another API can instead provide reference opponents or explicitly labeled demonstrations. Executable skill libraries have precedent in Voyager, which used prompting and code without parameter fine-tuning. [Voyager](https://arxiv.org/abs/2305.16291)

## Bounded league

Maintain **at most eight active model-policy snapshots per environment**, separate from two fixed diagnostic opponents. Pin the original base policy and the current candidate. Reserve two slots for recent predecessors, two for older policies that expose distinct weaknesses, and two for deterministic reservoir samples from historical versions. Collapse duplicate identities and fill unused slots from history. This is a bounded policy population, not a requirement to keep eight models resident in GPU memory.

Select/prune only using development matches and historical matchup diversity. Protect an older policy that reliably exploits a new one even if its scalar rating is low. Remove it from the active roster only when another retained policy covers that matchup behavior. Keep its checkpoint and complete historical record on disk; pruning the active roster does not mean deleting research evidence. Population-based opponent mixtures are motivated by PSRO's treatment of overfitting to co-adapting policies. [PSRO](https://arxiv.org/abs/1711.00832)

For each proposed next cycle, use 16 training episodes per game: eight versus current self, four versus the latest predecessor, and four versus the selected historical mixture. Use independent training scenario families and balance the learner's seat in the frozen-opponent games. Train both seats only when both used the current behavior policy; retain frozen-opponent actions for replay but exclude them from learner likelihood updates. Freeze the opponent mixture for the entire collection/update cycle.

Each new candidate plays development matches against the base, the game heuristic, and its predecessor: six scenario seeds with both seats per pairing, or 36 matches per game. For an eight-policy roster, perform a bounded diversity refresh of one paired scenario for every unordered policy pair (56 games per environment); these are noisy diagnostics, not precise ratings. Rotate independent development seeds across refresh periods. Training and rating schedules have separate seeds.

Before a final claim, run an untouched evaluation against fixed base/heuristic references on at least 24 new paired scenario seeds per game, and report all environments. This final test is consumed once per declared comparison. More precision, multiple training seeds, and matched-compute fixed-opponent controls remain necessary for a convincing research result.

## Ratings and nontransitivity

Provide the requested **Elo-style history separately for each environment, rule version, horizon, and policy interface/computation allowance**. Anchor the base at an arbitrary documented value such as 1000. Ratings are internal to this experiment and are not human chess ratings. Save the match log and rating algorithm/version so any history can be recomputed.

For a transparent Elo display, map a positive game outcome to 1, a tie to 0.5, and a negative outcome to 0; choose the K factor before matches and update both ratings from their pre-match values. Process matches in a fixed order or use a documented batch fitting procedure. Scores based on material/distance cutoffs must be explicitly named **16-ply material-adjudicated chess** and **8-round distance-adjudicated maze**. Do not silently count unfinished games as ordinary chess/maze victories. Keep continuous reward, absolute P&L, goals, mates, and cutoff rates alongside ratings because sign-only scores discard margins and objectives.

A rating-deviation estimate or scenario-bootstrap uncertainty is preferable to a precise-looking point rating. Glicko-2 explicitly models uncertainty and recommends reasonably sized rating periods; it does not make three scenario seeds sufficient evidence. Paired games share a scenario, so uncertainty must resample scenario pairs rather than individual moves. [Glicko-2 specification](https://www.glicko.net/glicko/glicko2.pdf)

Always display a checkpoint cross-play matrix beside the rating curve. A beats B, B beats C, and C beats A is possible; a scalar ranking cannot capture that cycle. Preserve pairwise outcomes and empirical payoffs so population methods, including a later alpha-Rank analysis, remain possible. Pruning solely by Elo can discard valuable counterstrategies. [Alpha-Rank](https://arxiv.org/abs/1903.01373)

## Resuming without changing the experiment

The next runner must checkpoint at explicit boundaries. Save model/adapters, optimizer state, RNG states, pending minibatch position, normalization/baseline state, league roster, and the immutable behavior-policy identity. Store rollout stages and match IDs in an append-only journal with atomic completion markers. Reconcile completed matches before resuming; never silently duplicate them in training or ratings.

Before resume, verify model/tokenizer revisions, source archives, environment versions, schedule, reward formula, opponent hashes, sampling settings, and dataset hashes. A changed configuration starts a new experiment. If a mid-update checkpoint lacks optimizer/RNG state, restart that update from its saved pre-update checkpoint and frozen rollouts, clearly recording the restart. The present `arena-v1` trainer is not assumed to support mid-epoch resume.

Preserve all final evaluations, candidate generation attempts, selected and rejected checkpoints, raw simulator trajectories, sampled probabilities, code artifacts, and ledger entries. A stopped or failed run remains visible. Keep one fixed anchor population and unchanged rating references as older opponents leave the active roster, so apparent rating gains cannot come merely from opponent removal.
